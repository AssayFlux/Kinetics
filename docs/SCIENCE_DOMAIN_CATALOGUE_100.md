# Kinetics scientific and healthcare acquisition taxonomy — 100 foundational + 60 extension domains

**Purpose:** define the foundational 100 biomedical/healthcare domains and link them to 60 cross-disciplinary extension domains, for a unified 160-domain acquisition scope spanning biological science, medicine, computing, engineering, chemistry, physics, Earth systems and human resilience.

**Status rule:** inclusion means a domain is in scope for integration planning. It does not mean a complete dataset, validated model, clinical workflow or production capability already exists.

## Integration requirements

| Contract | Minimum requirement |
|---|---|
| Identity | Stable source identifiers; explicit entity and record keys |
| Provenance | Source, version, retrieval time, checksum, citation and processing history |
| Rights | License, consent basis, access conditions and redistribution restrictions |
| Semantics | Versioned domain schema, units, controlled vocabularies and mappings |
| Quality | Validation rules, missingness, duplicate/conflict handling and rejection reports |
| Evidence | Study design, population, limitations, uncertainty and review status |
| Security | Data classification, minimization, access control, audit and retention |
| Compute | Resource budget, resumability, isolation and reproducible environment |
| Validation | Domain-specific reference datasets, benchmark protocol and acceptance criteria |
| User safety | Intended use, prohibited uses, human review and abstention rules |

## Implementation discipline

1. Build shared identity, provenance, licensing, ingestion, storage, indexing, search and evidence contracts.
2. Integrate domains in dependency-aware waves; do not force incompatible records into one generic schema.
3. Prefer authoritative source registries and documented APIs; acquire only data whose terms permit the intended use.
4. Keep clinical, genomic, imaging and other sensitive data behind consent, privacy, governance and access controls.
5. Treat treatment comparisons and patient-level outputs as research until independently validated for a defined intended use.
6. Build the application after the integrated foundation and stable APIs; perform comprehensive system acceptance and model training after integration.
